Del caos por correo a la trazabilidad tipo Git

Reemplazamos el intercambio manual de archivos sueltos por un ciclo formal de Propuesta de Cambio auditable de punta a punta.

Flujo tradicional (hoy)

  • Versiones sueltas: Tesis_v3_revisada_final2.tex enviadas por correo sin historial ni diff.
  • Retroalimentación dispersa: observaciones en PDFs o mensajes sin anclaje a línea ni estado de resolución.
  • Riesgo de fuga de datos: tesistas subiendo borradores inéditos a APIs comerciales de IA.

Flujo TesisHub (MVP)

  • Espacio de Trabajo: inicializado desde plantilla institucional LaTeX o archivo .zip validado.
  • Revisión en 2 etapas: pre-revisión automática con IA local + dictamen formal del asesor sobre diff línea por línea.
  • Consolidación segura: fusión fast-forward only a main tras aprobación y 0 comentarios activos, con compilación PDF.

Metodología Multi-Agente Maker–Checker

Separar quién escribe el código de quién lo audita elimina el sesgo de confirmación del LLM.

Maker: Claude Code CLI

Generador
  • Invocado en modo headless no interactivo (claude -p) por historia de usuario.
  • Lee directivas estrictas en CLAUDE.md y AGENTS.md del repositorio.
  • Implementa código, migraciones y pruebas; ejecuta el CI local antes de abrir el Pull Request.
  • Atiende hallazgos bloqueantes en ciclos iterativos hasta lograr aprobación.

Checker: Antigravity (Gemini)

Auditor Empírico
  • Subagentes efímeros con contexto 100% limpio por cada ronda de auditoría (pr-audit).
  • Verifica criterios de aceptación de Jira, arquitectura hexagonal y reusabilidad.
  • Regla de oro: prohibido reportar bugs por intuición; todo defecto debe reproducirse con un test que falle.
  • Convergencia pragmática: máximo 3 rondas; aprueba automático si solo quedan NIT menores.

Auditoría empírica guiada por pruebas

"Ningún bug se reporta sin una prueba ejecutable que falle" — eliminamos las alucinaciones en code review.

Clasificación estricta de hallazgos

  • BUG_CONFIRMADOBloqueante. Incluye código @Test o spec.ts que falla reproduciendo el defecto.
  • AC / ARQUITECTURABloqueante. Violación de criterio de aceptación en Jira o de capas hexagonales.
  • CALIDAD / REUSOBloqueante. Duplicación, complejidad excesiva o falta de cobertura.
  • NITNo bloqueante. Sugerencias menores de estilo; si solo quedan NITs, el PR se aprueba.

Flujo de verificación en pr-audit

  • 1. Si el Checker sospecha un bug, escribe la prueba en su worktree *-audit y la ejecuta.
  • 2. Si la prueba pasa en verde → era un falso positivo; se descarta sin ruido en el PR.
  • 3. Si falla → se publica el hallazgo con el código del test en GitHub PR y en Jira.
  • 4. El Maker incorpora ese mismo test a la suite oficial y corrige el código hasta ponerlo en verde.

Infraestructura Docker y gates obligatorios

Cada PR debe superar la pirámide completa de pruebas en local y en GitHub Actions antes de ser auditado.

Pirámide de pruebas (5 niveles)

  • Nivel 1–2 (Backend): Unitarias JUnit 5 + Integración MockMvc / Testcontainers PostgreSQL + JaCoCo ≥ 80% + Spotless.
  • Nivel 3 (Frontend): Jest unitarias (> 99% statements) + validación de contrato OpenAPI (api:check).
  • Nivel 4 (Caja negra HTTP): REST Assured contra contenedor Docker (docker-compose.api-tests.yml) + emisor sintético Fake Entra ID (HUB-83).
  • Nivel 5 (E2E + A11y): Playwright en Chromium + auditoría automática de accesibilidad con Axe (0 violaciones).

Comandos Gate por repositorio

tesishub-backend

./mvnw spotless:apply && ./mvnw verify

tesishub-frontend

npm run api:check && npm run typecheck && npm run lint && ng build && npm run test:coverage && npm run test:e2e

tesishub-infra

docker compose -f <file> config --quiet

Hallazgos críticos interceptados antes de develop

Casos reales donde la auditoría guiada por pruebas bloqueó defectos que habrían pasado una revisión superficial.

HUB-87 · Seguridad ZIP

Desbordamiento 64-bit en ZIP64

Entradas ZIP64 con tamaños combinados mayores a Long.MAX_VALUE hacían wrap-around a negativos, burlando la defensa contra bombas de compresión (RV-08).

Test: rv08RejectsZip64DeclaredSizesWhoseSumOverflowsLong

HUB-87 · Integridad Stream

Entradas omitidas en ZipInputStream

Un archivo ZIP cuyo directorio central declaraba entradas ausentes en la secuencia de headers locales lograba evadir la validación estándar.

Test: rv01RejectsAZipWhoseDirectoryListsEntriesMissingFromTheStream

HUB-48 · Persistencia

Colisión users_email_key y CRLF

El Checker reprodujo fallos al intercambiar correos en el seed SQL repetible y saltos de línea Windows CRLF en fixtures .mdx que rompían la regla ARC-02.
